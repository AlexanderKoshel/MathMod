# Описание устройства проекта

Создавать файл `SKILL.md` внутри готового проекта или задания. Образец структуры — `D:/BSU/Web/Task_1/SKILL.md`, первоначальная часть про React до позднейших дополнений Angular. Использовать структуру образца, а содержимое получать из текущих файлов целевого проекта. Если образец недоступен, использовать схему ниже.

## Подготовка

Прочитать исходники, конфигурацию зависимостей, условие, план и существующее описание. Проверить точки входа и команды запуска. Не переносить React, Webpack или другие технологии из образца в проект, где их нет. Если проект пока не реализован, описывать только существующие файлы и явно отметить статус; будущие файлы оставить в плане.

## Структура создаваемого SKILL.md

1. YAML frontmatter: `name` в lowercase-with-hyphens и `description` с назначением именно этого проекта.
2. Название проекта и границы: какая папка описывается, предмет, задание, вариант и текущее состояние.
3. **Структура проекта**: таблица «Папка / Файлы / Назначение». Отдельно отметить генерируемые результаты и установленные зависимости.
4. **Архитектура и порядок выполнения**: используемый стек с проверенными версиями; точка входа; порядок вызовов, преобразований и передачи данных; входы и выходы; роль каждого слоя. Отделять сборку от выполнения, вычисления от вывода результатов.
5. **Описание каждого файла**: отдельный блок для каждого собственного исходника, конфигурации, теста и документа. Формат блока приведён ниже.
6. **Запуск и проверка**: воспроизводимые команды с рабочей папкой, входными данными и ожидаемыми результатами; указать, какие команды действительно проверены.
7. **Генерируемые файлы**: таблица путей, содержимого, создающей команды и правил отслеживания в Git. Не перечислять каждый файл установленных пакетов.
8. **Правила дальнейшей работы**: конкретные инварианты проекта и какие связанные документы обновлять при изменениях.
9. **История версий**: дата, версия, изменённые файлы, изменение поведения и выполненные проверки. Начать с фактической первой версии; не выдумывать предыдущие релизы. Новые записи дописывать, сохраняя старые. Допустима история по разделам, если изменения остаются прослеживаемыми.

## Формат блока файла

```markdown
### ФАЙЛ: `путь/относительно/проекта`

**КАКИЕ ФУНКЦИИ ВЫПОЛНЯЕТ:** краткое назначение и наблюдаемое поведение.

**КАКИЕ ИСПОЛЬЗУЕТ МЕТОДЫ БИБЛИОТЕКИ:** конкретные используемые API, функции, классы, команды или технологии и зачем они нужны. Для декларативного файла указать формат и интерпретатор; если вызовов нет — написать это.

**ЗАВИСИМОСТИ И ВЗАИМОДЕЙСТВИЯ С ДРУГИМИ ФАЙЛАМИ:** входы, выходы, импорты, вызывающий код, конфигурация и направление передачи данных. Различать стандартную библиотеку, сторонние пакеты и собственные модули.
```

Для одинаковых ролей допускаются короткие блоки, но каждый собственный файл должен быть однозначно указан. Сгенерированные артефакты и внешние материалы описывать отдельно. Сверить список с деревом Git и доступными исходниками; не заявлять проверку, которая не выполнялась. При изменении проекта синхронно обновить описание файлов, архитектуру, THEORY.md и запись истории.
