# Учебный репозиторий

## Структура репозитория

Восстановлено по исходным правилам пользователя из чата «Анализ репозитория проекта» от ноября 2026 года. Не создавать README.

```text
main
├── materials/                  Материалы предмета
├── formatting-requirements/    Оригиналы требований к оформлению
├── lab-01/                    Отдельная папка задания
│   ├── <оригинал условия>      Исходный файл без подмены пересказом
│   ├── PLAN.md                План, критерии, команды и статус
│   ├── THEORY.md              Теория и вопросы для защиты
│   ├── SKILL.md               Устройство готового проекта
│   └── <код и конфигурация>    Структура определяется заданием
└── <другие задания>/
```

## Порядок работы

1. Проверить локальные инструкции, состояние Git, существующие материалы и оригинал задания. Установить предмет, вариант, ограничения и критерии сдачи. Если условия нет, запросить его; не выдумывать тему, алгоритмы, зависимости или результаты.
2. Для нового предмета создать репозиторий и связать его с выбранной пользователем локальной папкой. Проверить `origin` и доступ к удалённой ветке. Существующий репозиторий не заменять.
3. Основная ветка — `main`; она содержит папки всех завершённых заданий. Для каждой лабораторной или РГР создать от актуальной `main` отдельную ветку, например `lab-01`, и отдельную папку с заданием. Сохранять установленное в конкретном предмете именование.
4. Скопировать оригинал условия в папку задания. В `PLAN.md` зафиксировать источник и вариант, требования, этапы реализации с отметками выполнения, структуру файлов, проверки, критерии готовности, команды установки и запуска. Планируемое отделять от уже выполненного.
5. Подготовить `THEORY.md` по правилам ниже. Реализовывать только согласованный объём: запрос плана сам по себе не означает запрос готового решения.
6. После готовности проекта создать или обновить его `SKILL.md` с помощью скилла `project-file-guide` из соседней папки. Это описание конкретного проекта, а не копия универсального процесса.
7. Выполнить подходящие проверки; записать фактические результаты и оставшиеся ограничения. Коммитить и отправлять только относящиеся к заданию файлы. Не публиковать секреты, установленные библиотеки, виртуальные окружения и временные результаты.
8. После завершения задания слить ветку в `main` и отправить обе ветки. Незавершённое задание не помечать завершённым и не сливать под видом готового. Проверить соответствие локального и удалённого SHA; не объявлять синхронизацию по одному только успешному коммиту.

## Теория для защиты

`THEORY.md` начинается с заголовка «Оглавление» и ссылок на разделы. После оглавления указать лабораторную, вариант, источник задания и статус материала.

Включить все понятия, навыки, теоремы, методы, алгоритмы, технологии и зависимости, которые фактически нужны решению. Для математического метода дать обозначения, формулы, условия применимости, точность, ограничения и пример. Для теоремы дать условия и заключение, объяснить её использование в работе; если доказательство нужно по условию — привести его. Не приписывать методу гарантий без предпосылок.

Для каждой технологии объяснить назначение, используемые возможности и связь с файлами проекта. Версии брать из конфигурации и проверенного окружения. Указать источники теории. Покрытие проверить таблицей «требование / метод или технология / раздел теории / файл реализации»; до реализации последний столбец явно помечать как план.

В конце включить вопросы для репетиции защиты с краткими ответами, задачами на ручной расчёт, объяснением кода, граничными случаями и сценарием демонстрации. Обновлять теорию при изменении решения.
